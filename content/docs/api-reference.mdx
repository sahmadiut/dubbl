## Exchange rate inputs

`POST /api/v1/exchange-rates` accepts a batch of manual rates. Exact clients can
send a decimal string in `rateExact`:

```json
{
  "rates": [
    {
      "baseCurrency": "USD",
      "targetCurrency": "EUR",
      "date": "2026-10-02",
      "rateExact": "0.9",
      "rateDirection": "quote_per_base"
    }
  ]
}
```

This synthetic example means 0.9 EUR per 1 USD. The existing numeric `rate` input
remains integer millionths: `900000` represents the same quote. If both fields
are supplied, they must agree. `PUT /api/v1/exchange-rates/{id}` accepts either
alias too. Responses preserve numeric `rate` and return the normalized string
`rateExact`, direction and storage/provenance metadata.

During legacy coexistence, saved rates must fit 0.000001 through 2147.483647 with
at most six decimal places. A valid exact string outside that range returns HTTP
422 with `code: "LEGACY_NUMERIC_RANGE"` before writing any rate in the batch.
Invalid or conflicting aliases return 400. Same-currency quotes must equal 1.
Writes require `manage:tax-config` permission and operate within the authenticated
organization. Dates are Gregorian `YYYY-MM-DD`.

The MCP `set_exchange_rate` tool accepts `rateExact` too. Its original numeric
field, `rateDecimal`, is **unscaled** (0.9 in this example), unlike REST `rate`.
MCP historical inverse lookups return a string rounded to 18 decimal places
alongside a legacy numeric rate rounded to six places. The `convert_amount`
tool remains a legacy numeric preview for currencies with matching minor-unit
scales and safe intermediate products; full-range amount strings and mixed-scale
conversion are not available in that operation yet.

## Contact credit limits and balances

`POST /api/v1/contacts` and `PATCH /api/v1/contacts/{id}` accept an optional
`creditLimitMinor` canonical integer string alongside the numeric `creditLimit`:

```json
{"creditLimitMinor": "1250"}
```

This means the existing stored integer 1250 (USD cents for a USD contact).
Neither alias rescales history for another currency. Both fields must agree if
supplied together; `null` clears the limit, zero sets a zero limit, and omission
keeps the current limit on updates. Responses include numeric `creditLimit` and
nullable string `creditLimitMinor`. The MCP `create_contact` and `update_contact`
tools accept the same aliases; `list_contacts` and `get_contact` return them.

Current supported write range is 0 through 9007199254740991. Valid int64 strings
above this range return HTTP 422 with `code: "LEGACY_NUMERIC_RANGE"` before writes.
Malformed, negative or conflicting aliases return 400. Writes require
`manage:contacts`; existing organization and resource/currency-plan checks apply.

REST contact listings additionally return `owesYouMinor`, `youOweMinor` and
`overdueMinor` alongside their numeric fields. Sums are calculated exactly and
must fit the safe numeric range; numeric fields keep their existing cents units.
Nonzero outstanding documents must use the contact's currency. A page containing
incompatible currencies or unsafe totals returns 422 rather than combining
unlike currencies or rounding amounts. MCP contact listings retain their existing
shape without these balance aggregates. Full int64 business operations and
currency-grouped contact balance reporting are pending further rollout.

## Payment read amounts

`GET /api/v1/payments` and `GET /api/v1/payments/:id` preserve numeric
payment/allocation `amount` and add the matching `amountMinor` string in existing
currency minor units (USD cents). `1250` remains `1250` for every currency.
Related contacts add nullable `creditLimitMinor`; detail bank accounts add
`balanceMinor` and nullable `lowBalanceThresholdMinor` in their own currency.
List retains `{data, pagination}` with contact/allocations; detail retains
`{payment}` with contact/bank account/allocations. MCP `list_payments` and
`get_payment` return the same aliases in their existing envelopes.

Signed safe integer history from -9007199254740991 through 9007199254740991
is supported. Unsupported history or foreign nested/document/journal/statement
references returns 422 (`LEGACY_NUMERIC_RANGE`), preserving stored amounts.
Noncash credit/debit-note carrier allocations remain separate rows without
being summed into cash. Same-organization inactive/deleted references remain
readable as history; deleted payments return 404.

Lists accept `type=received|made`, a contact UUID, `page` (1..21474836) and
`limit` (1..100), defaulting to page 1 and limit 50. Invalid/fractional/out-of-range
filters or pagination return 400. Reads require existing authenticated
organization access and permit read-only roles. These aliases qualify reads;
settlement creation, batches, scheduled payments and reversals are covered below.
Full-int64 business operations retain separate rollout work.

## Payment settlement amounts

`POST /api/v1/payments`, `POST /api/v1/invoices/:id/pay` and
`POST /api/v1/bills/:id/pay` accept positive integer `amount` or canonical string
`amountMinor`, or both with exact agreement. Units are the document currency's
stored minor units (USD cents); no currency or magnitude rescales the input.
The same aliases apply to standalone payment allocations. Supported monetary
values and converted results must fit 1 through 9007199254740991; larger valid
int64 strings return 422 with `LEGACY_NUMERIC_RANGE` before committing writes.

Single-document requests require Gregorian `date` (`YYYY-MM-DD`) and optionally
`method`, `reference`, `bankAccountId` and `idempotencyKey`. Standalone creation
also requires `contactId`, `type` (`received` for invoices, `made` for bills) and
1-1000 distinct `allocations` containing `documentType`, `documentId` and either
amount alias. Optional `currencyCode` must match every document; omission derives
it. Allocations must fully cover cash for one contact/currency, without exceeding
outstanding balances. Use customer credits for unapplied cash.

All three operations require `manage:payments`, recognized outstanding documents
with qualified saved journals, an open payment date on/after recognition, and an
active organization-owned bank in the document currency when supplied. Cash posts
to the linked bank GL account, or code 1100 when omitted. Bill settlement subtracts
the actual payable, including reverse-charge handling. Document balances, cash,
allocation rows, saved-FX control release, realised FX and audit commit atomically.
Missing rates, unqualified historical annotations/carriers and unsupported FX or
rounding return explicit errors. Historical recognition rates are never reloaded
from current quotes; final settlement releases the saved rounding remainder.

Creation returns `{payment}` (201) with contact and allocations. Invoice/bill pay
returns `{invoice,payment}` or `{bill,payment}` (200), retaining numeric header
amounts and adding matching `*Minor` strings; payment includes `amountMinor`,
`currencyCode` and `journalEntryId`. MCP `create_payment`, `pay_invoice` and
`pay_bill` use these contracts; single-document MCP dates default today in UTC.
MCP single-document payments now create actual cash/GL records and require
payment permission; their former balance-only annotation behavior is replaced.

Supply `Idempotency-Key` or body/tool `idempotencyKey` (1-128 ASCII letters,
digits or `._:-`) for retries. Header/body aliases must agree. Keys are shared
across these settlement operations within the organization: equivalent normalized
requests return the original response, while changed operations/data return 409.
Amount alias choice and allocation order do not change the request identity.
Specify the date on retrying MCP calls across days. Without a key each successful
call records new cash. Retry/provenance guarantees require retaining the payment
settlement audit row; ordinary references are not retry keys.

## Payment batches

`POST /api/v1/payments/batch` and MCP `record_payment_batch` record **one** payment
for multiple distinct documents of one contact/currency. Each allocation's
numeric `amount` is decimal **major** units (USD `12.50`), with optional
`amountExact: "12.50"` and `amountMinor: "1250"` aliases. Major aliases must agree
exactly; minor aliases must equal the rounded major value. Total is the sum of
rounded allocations. Currency scales apply to new inputs (JPY/IRR `1250` major,
KWD `1.250` major all become `1250` minor); existing history is never rescaled.
Positive ties round up using exact ratios. `date` is required. Optional method,
bankAccountId, reference and idempotencyKey follow payment settlement rules.
Requires `manage:payments`, recognized outstanding documents and open periods.
Returns `{payment}` (201) with numeric minor amounts and `amountMinor` strings.

| Method | Path | MCP |
|---|---|---|
| GET / POST | `/api/v1/payment-batches` | `list_payment_batches` / `create_payment_batch` |
| GET / PATCH | `/api/v1/payment-batches/:id` | `get_payment_batch` / `update_payment_batch` |
| POST | `/api/v1/payment-batches/:id/submit` | `submit_payment_batch` |
| GET | `/api/v1/payment-batches/:id/remittance` | `generate_remittance` |
| POST | `/api/v1/payment-batches/:id/remittance` | `send_payment_batch_remittance` |

Stored batch creation requires `name`, optional `currencyCode` (USD default), and
`items` with billId/contactId, numeric integer **minor** `amount` or matching
`amountMinor` string, and currencyCode (USD default). All 1-1000 distinct bills
must be recognized, outstanding and match their supplier and batch currency.
PATCH accepts name, addItems and removeItemIds on drafts only. Returns `{batch}`;
list retains `{data,pagination}`. Header totalAmount and item amount add *Minor
strings; detail/edit/submit expand bill money aliases and contact creditLimitMinor.

Submission posts one bank_transfer payment per item on today's UTC date using
GL 1100. All cash, GL, balances, numbering, item/batch status and mandatory audits
commit together. Any failure leaves the draft unchanged. Returns
`{batch,processed,total}`; repeated/concurrent submission cannot duplicate cash.
Amounts, totals and converted journal sides must fit the safe numeric range
(maximum `9007199254740991` minor units). Larger exact inputs fail 422 before
commit. No exact-only representation or production IRR enablement is implied.

Remittances require completed items and qualified linked live payment history.
They return `{batch,remittances}` with numeric totalAmount/totalPaid/billTotal/
amountPaid and corresponding *Minor strings. Drafts reject; legacy batches
without settlement linkage fail 422; reversed cash fails 409. Sending accepts
optional supplier contactId and plain text personalMessage, preflights all groups,
and returns sent/skipped lists. Missing email skips. Email delivery is sequential;
provider failures can leave earlier deliveries committed, and repeats can resend.

## Scheduled payments

| Method | Path | MCP |
|---|---|---|
| GET / POST | `/api/v1/scheduled-payments` | `list_scheduled_payments` / `create_scheduled_payment` |
| GET / PATCH / DELETE | `/api/v1/scheduled-payments/:id` | `get_scheduled_payment` / `update_scheduled_payment` / `delete_scheduled_payment` |
| POST | `/api/v1/scheduled-payments/process` | `process_scheduled_payments` |

Create requires billId, contactId, scheduledDate and positive integer minor-unit
`amount` (USD cents) or canonical `amountMinor` string, or both with exact agreement.
Currency defaults to USD and must match the bill; existing minor amounts never
rescale. Optional notes is nullable. Scheduling requires a recognized outstanding
supplier bill, matching organization/contact/currency, no overpayment and an open
Gregorian posting date on/after recognition. Amounts and converted results must
fit 1..9007199254740991. Larger exact int64 values fail 422 before mutation.

PATCH edits pending schedules' amount aliases, scheduledDate or notes, or cancels
with `status:"cancelled"`. Old/new dates must be open. DELETE soft-deletes only
pending, cancelled or legacy failed schedules; it never reverses cash. Processing
or completed schedules reject deletion. Writes/process require `manage:payments`;
reads permit authenticated read-only roles. CRUD/audit writes are atomic.

Create/detail/edit return `{scheduledPayment}`, retaining numeric amount and adding
amountMinor plus expanded bill money *Minor/contact creditLimitMinor strings.
List returns `{data,pagination}` with optional status and page/limit (1/50 defaults,
limit capped at 100). Unsupported money or foreign nested references fail explicitly.

Process uses today's UTC date as the due cutoff, posting each pending item on its
saved scheduledDate via bank_transfer and GL 1100. Exact settlement, retained
currency/carrying/FX, bill balance, ledger, numbering, schedule completion and
mandatory audits commit together per item. Concurrent/repeated processing cannot
duplicate completed cash. Failed items roll back and remain pending for retry;
legacy failed/processing rows are not retried. Independent successes stay committed.
Returns `{processed,total,skipped,failed,failures:[{scheduledPaymentId,status,error,code?}]}`.
Inspect failed/failures even on HTTP 200 or successful MCP calls. No automatic
background cash-posting job is added. Multiple schedules do not reserve a balance;
current outstanding is rechecked at execution. Repeated create makes new intent.

## Payment reversals

`DELETE /api/v1/payments/:id` and MCP `delete_payment` accept an organization
payment UUID and return `{success:true}`. There is no money input or currency
conversion. Both require `manage:payments` and open payment/document/credit dates.
They restore invoice/bill paid/due/status and clear `paidAt`, restore paired
credit/debit-note or prepayment balances, reverse the saved cash/application
journal verbatim (including exact FX and dimensions), and soft-delete/audit in
one transaction. Note recognition and original prepayment deposits are retained.
Allocation rows and bank/reference metadata remain available as history.

Saved amounts and balance sums must fit safe integer minor units (USD cents);
invalid/foreign/ambiguous or unsupported history returns 422 before committed
mutation. Bank-matched or provider-backed payments return 409 until unmatched
or refunded through the appropriate workflow; deletion does not issue a refund.
Missing/deleted payments return 404, including repeated deletes. No cash entry
or audit is duplicated. Settlement retry keys continue to replay original results;
use a new key when recording new cash after reversal.

Reversal never reloads current exchange rates or changes saved rounding. If
out-of-order reversals leave rounded carrying that fails the settlement guard,
unwind the remaining applications before recording cash again. Full-int64 and
generalized residual-carrying qualification remain separate work.

## Budget amount inputs

Budget POST/PATCH requests accept string aliases for signed integer cents:

```json
{
  "lines": [{
    "accountId": "your-account-uuid",
    "totalMinor": "1250",
    "periods": [{
      "label": "January",
      "startDate": "2026-01-01",
      "endDate": "2026-01-31",
      "amountMinor": "1250"
    }]
  }]
}
```

Supply the usual budget header fields on creation. Numeric `total`/`amount`
remain supported and must agree with their string aliases when both are present.
Amounts retain the existing cents units; no currency rescaling occurs. Missing
period amounts default to zero. An explicit line total keeps precedence over
period sums; otherwise the sum becomes the total. Omitted/empty periods generate
from the effective header dates/type and distribute the total exactly, including
negative amounts. Dates are valid Gregorian date-only values with UTC boundaries.

Supported amounts and per-line period sums are -9007199254740991 through
9007199254740991, with at most 500 lines and 10000 periods per budget. Valid int64
strings outside the supported amount range return 422 (`LEGACY_NUMERIC_RANGE`)
before writes; malformed/conflicting aliases return 400. Account/fiscal-year refs
must belong to the authenticated organization. Create and replacement writes are
transactional and require `manage:budgets`.

GET by ID returns numeric fields alongside `totalMinor`/`amountMinor`. Lists and
create/update responses keep their header-only envelopes. MCP budget CRUD tools
accept/return the same aliases. Budget-versus-actual reports and frontend amount
arithmetic are still awaiting exact-money rollout; CRUD support does not establish
full-range reporting or production IRR readiness.

| POST | `/api/v1/invoices/:id/approve` | Approve the assigned workflow step |
| POST | `/api/v1/invoices/:id/reject` | Reject the assigned workflow step |

Lifecycle responses retain numeric minor-unit totals and add matching `*Minor`
strings. Write-off defaults to `{action:"write-off",method:"direct"}`; allowance
is also supported. Recovery uses `{action:"recover",amount:1250}` or
`{action:"recover",amountMinor:"1250"}` in integer invoice-currency minor units;
omission defaults to invoice total. Interest overrides use decimal-major
`amount:12.5` or `amountExact:"12.50"`, or integer-minor `amountMinor:"1250"`
for USD. Dual aliases must agree. Calculated simple/daily compound interest uses
exact ratios and one final rounding; overdue duration supports up to 36500 days.
Recovery and interest responses add `recoveredMinor` and `interestAmountMinor`.

Send/void/bad-debt/approval decisions require `approve:invoices`; interest charges
and approval submission require `manage:invoices`. Issue-date locks are checked,
and interest checks today's posting date too. Sending requires complete active
revenue/control accounts and agreeing nonnegative line/header balances. Voiding
settled invoices requires refunding/unapplying payments or credits first. Each
operation commits its accounting/status/stock/approval effects atomically; saved
FX is retained, and voiding reverses stored amounts without reconversion.
Optional send email runs after accounting commits; delivery failures should be
retried using email operations. Monetary values remain within safe integer range;
unsupported amounts/FX return 422 instead of being rounded into legacy fields.
Matching MCP tools include `send_invoice`, `void_invoice`, `write_off_invoice`,
`recover_written_off_invoice`, `calculate_invoice_interest`,
`charge_invoice_interest` and the submit/approve/reject invoice tools.

Invoice list/detail reads retain numeric `subtotal`, `taxTotal`, `total`,
`amountPaid` and `amountDue` in stored minor units (USD cents), alongside exact
`*Minor` integer strings. Detail lines add `unitPriceMinor`, `amountMinor` and
`taxAmountMinor`; nested contacts add nullable `creditLimitMinor`. Quantities and
discount basis points retain their existing units. REST allocated payments add
`amountMinor`; MCP `get_invoice` retains its `{invoice}` envelope.

REST detail base amounts add nullable `*Minor` strings and an explicitly
lookup-derived `rateExact`/`rateDirection`/`rateBasis`. Base display supports matching
currency scales and safe FX products. It does not report saved invoice posting FX.
Summary returns numeric/string outstanding, overdue and aging amounts with one
`currencyCode` (null when empty). Mixed-currency outstanding invoices and unsafe
amounts/totals return 422 `LEGACY_NUMERIC_RANGE`. All numeric money remains limited
to the safe integer range. MCP `list_invoices`, `get_invoice` and
`get_invoice_summary` expose the same scoped read contracts.

Invoice create and draft update accept legacy decimal-major `unitPrice` numbers,
exact decimal-major `unitPriceExact` strings and integer-minor `unitPriceMinor`
strings. Aliases must agree: USD `12.50` maps to `1250` minor units. Numeric money
and exact inputs currently support only the safe integer monetary range. Quantity
is decimal physical units; discount is basis points. Create/update responses retain
`{invoice}` with numeric minor totals plus `*Minor` strings; create also returns
nullable `creditLimitWarning` with numeric/exact amounts. Draft deletion returns
`{success:true}`. MCP `create_invoice`, `update_invoice` and `delete_invoice` use
the same scoped atomic CRUD services and require `manage:invoices`.

REST create rounds unit price before quantity multiplication; draft update and
MCP create round the extended major price. Send `unitPriceExact` for sub-minor
precision. REST missing prices use price-list/item defaults; MCP retains zero
unless a price list is specified, and update omission remains zero. Price-list
currency must match; inventory fallback requires organization currency. Create
currency defaults to contact/org/USD in REST, USD in MCP. Old/new issue-date locks,
owned references and safe totals are checked before writes. Hard credit limits
return 403; mixed-currency credit comparisons and unsafe money return 422.
Lifecycle and bulk routes retain their separate contracts.

Quote responses retain numeric currency minor units and add `subtotalMinor`,
`taxTotalMinor`, `totalMinor`, `billedTotalMinor`. Detail lines add
`unitPriceMinor`, `amountMinor`, `taxAmountMinor`; contact adds `creditLimitMinor`.
The list keeps `{data, pagination}`. Currency defaults to USD in both transports.

REST line `unitPrice` remains decimal major units; MCP `create_quote` and
`update_quote` numeric `unitPrice` remains integer minor units (USD cents).
Both accept `unitPriceExact` (decimal major-unit string) and `unitPriceMinor`
(canonical integer minor-unit string). Supplied aliases must agree: REST major
aliases agree exactly, minor aliases agree with the rounded major price. Prices
round before extending by physical quantity. Quantity is physical units on input,
hundredths on output; discounts and tax rates use basis points. Tax is exclusive.
All monetary inputs, individual rounded products and sums must fit the safe
integer range; larger exact strings return 422 without writes.

PATCH accepts contact, Gregorian issue/expiry dates, reference, notes, currency
and replacement lines. Retained minor amounts are never rescaled by currency
edits. Arbitrary database fields (including status, tenant and header totals) are
rejected. Replacement prices default to zero, with no price lookup. Creation
supports item/list lookup; items are lookup-only, and list currency must match.

Conversion accepts an empty body, `percentage` greater than zero through 100,
or `lines: [{quoteLineId, quantity}]`; nonempty lines take precedence. Percentage
bills a share of the original total, rounded per original line; omission bills the
exact remaining balance with deterministic residual allocation. It returns
`{quote, invoice, billing}` with numeric `invoiced`, `billedTotal`, `remaining`,
matching `*Minor` strings and `fullyBilled`. Partial bills remain accepted; only
zero remaining marks converted. Overbilling returns 400 with numeric/exact
`remaining` and `requested`. Malformed conversion JSON returns 400.

All writes require `manage:invoices`, organization-owned references and unlocked
issue dates; conversion also checks today's invoice date (UTC). Numbering,
headers, lines and billing totals commit atomically. Matching MCP operations are
`list_quotes`, `get_quote`, `create_quote`, `update_quote`, `delete_quote`,
`send_quote`, `accept_quote`, `decline_quote`, `convert_quote_to_invoice`.
MCP send records status only; REST email delivery follows the committed status
change and can fail independently. PDF/public/provider paths retain separate
contracts.

Numeric money retains currency minor units and adds corresponding `*Minor`
strings. Credit-note headers include subtotal/tax/total/applied/remaining aliases;
lines include price/amount/tax aliases. Customer credits include original/remaining
aliases. Summary adds exact total/status amounts and rejects mixed currencies.
Available credits include `amountDueMinor` for the invoice and credit aliases.

REST line `unitPrice` remains decimal major units; MCP numeric prices are integer
minor units. Both accept `unitPriceExact` (decimal major string) and `unitPriceMinor`
(canonical minor string). Aliases must agree. Credit lines extend the unrounded
major price by physical quantity, then round gross/discount/exclusive tax; quantities
are physical units on input and hundredths on output, discounts basis points.
Creation defaults currency to USD and omitted prices to zero. PATCH permits
contact, original invoice, Gregorian issue date, reference, notes, currency and
replacement lines; arbitrary tenant/status/header-total fields reject.

Customer-credit create and both application operations accept positive integer
minor `amount` or canonical `amountMinor`, agreeing when both supplied. All money,
rounded products, taxes, sums and converted amounts must fit the JavaScript safe
integer range; larger valid exact inputs return 422 without committed changes.
Customer-credit currency defaults contact/org/USD; creation requires exactly one
cash `bankAccountId` or asset `depositAccountId`, and bank currency must match.
Application optionally accepts Gregorian `date` for customer credits, defaulting
to today (UTC). Both credit types require matching invoice customer/currency and

Statement sums use exact integer arithmetic and reject mixed currencies. Existing
invoice selection and descending date order remain. Quantity is still hundredths
and discount percentages are basis points; monetary strings never rescale values.

MCP counterparts are `get_payment_link`, `get_portal_identity`,
`list_portal_invoices`, `list_portal_payments`, `list_portal_quotes`,
`get_portal_statement` and `accept_portal_quote`. All require the token to belong
to the authenticated organization. Reads require `view:data`; acceptance requires
`manage:invoices` and a `quoteId` UUID. Inputs are strict and accept no amounts.

## Exact recurring invoice prices

Recurring invoice endpoints (`/api/v1/recurring-invoices` and invoice targets of
`/api/v1/recurring`) and MCP `create_recurring_template` with `type: "invoice"`
accept additive `unitPriceExact` decimal-major strings and `unitPriceMinor`
canonical currency-minor integer strings alongside numeric decimal-major
`unitPrice`. For USD, `12.50`, `"12.50"` and `"1250"` denote the same price.
If several aliases are supplied, they must agree. Stored line `unitPrice` remains
numeric minor units and gains `unitPriceMinor`; preview `lineTotal` gains
`lineTotalMinor` and a currency code. Preview totals remain before discount/tax.

Prices, line products and totals must fit safe integers (absolute value at most
9007199254740991). Invalid aliases reject before writes. Schedule dates use
Gregorian `YYYY-MM-DD`, occurrence caps fit int32, and every reference belongs to
the organization. Template FX inputs are unsupported; automated posting resolves
historical FX for each occurrence and saves exact posting rates. Changing currency
across minor-unit scales requires a new template with explicit prices.

Generation atomically commits invoice numbers, documents, automated posting and
schedule advancement per template. Locked dates, missing posting FX or invalid
saved data leave the schedule pending for retry. Auto-send attempts email after
commit; delivery failure retains the posted invoice. MCP also provides
`delete_recurring_invoice` and `preview_recurring_invoice`. Other document types
retain their existing numeric price contracts.

## Bulk invoice contracts

| POST path | Input | Result |
|-----------|-------|--------|
| `/api/v1/bulk/invoices/preview` | `{source?, rows}` | Preview, validation counts and exact totals |
| `/api/v1/bulk/invoices/import` | `{fileName, source?, rows}` | `{job}` (201), document counts/errors |
| `/api/v1/bulk/invoices/send` | `{ids}` (1 through 100) | `{updated, ids}` |
| `/api/v1/bulk/invoices/mark-paid` | `{ids}` (1 through 100) | `{updated}` |
| `/api/v1/invoices/bulk` | `{action, invoiceIds}` (1 through 200) | Per-invoice results and summary |

Import accepts nested documents with `contactId`, `issueDate`, `dueDate`, optional
`reference`/`currencyCode`, and `lines`. Numeric `unitPrice` is decimal major units;
`unitPriceExact` is decimal-major text and `unitPriceMinor` is an integer minor-unit
string. Aliases must agree. Currency defaults to USD for import; explicit currency
determines its scale. Prices, products and sums must fit safe integers. Imported
lines retain extended-price rounding, with quantity stored in hundredths.

Flat mapped CSV rows use `lineDescription`, `lineQuantity`, `lineUnitPrice`,
`lineUnitPriceExact`, `lineUnitPriceMinor`, `lineAccountId` and `lineTaxRateId`.
They group by `invoiceNumber`, otherwise contact/date/reference; all group headers
must agree. Supply Dubbl contact/account UUIDs. CSV prices are canonical decimal
text, and string quantities have at most two fractional digits. Source selects date
preprocessing only. Generated invoice numbers use the organization's sequence.

Malformed or unsupported money fails before import job creation. Business errors
are reported per document, with each number/header/lines committed atomically.
Repeating an import creates new documents; inspect job results before retrying.
Preview adds numeric `subtotal`, `taxTotal`, `total` and matching `*Minor` strings.
Import jobs count grouped documents, not physical CSV lines.

Bulk send and `action: "mark-as-sent"` require `approve:invoices` and atomically
recognize all qualifying drafts with their journals, stock effects and snapshots.
They send no email; one failing eligible document rolls back the batch. Foreign,
deleted and non-draft IDs are ignored. Repeating a successful send updates zero.

Bulk mark-paid requires `manage:invoices` and remains a compatibility annotation
for invoices settled outside Dubbl. It records no payment, allocation or settlement
journal. Only sent/partial/overdue invoices with consistent safe balances and
unlocked issue dates qualify; the update is atomic. Use payment operations to
record an accounting settlement.

`action: "send-reminder"` requires `manage:recurring` and verified organization
email. Saved money/references preflight before delivery; delivery failures are
reported per item. Repeating can send another reminder. MCP counterparts are
`preview_invoice_import`, `import_invoices`, `bulk_mark_invoices_sent`,
`bulk_mark_invoices_paid` and `bulk_send_invoice_reminders`.

## Purchase order exact contracts

`/api/v1/purchase-orders` supports list/create; `/:id` supports detail/draft
edit/delete; `/counts` returns status buckets; `/:id/send` marks a draft sent;
`/:id/convert` creates a draft bill. Prices use decimal-major numeric `unitPrice`,
exact decimal-major `unitPriceExact` or integer minor-unit `unitPriceMinor` strings.
Aliases must agree. Currency defaults USD. Physical quantities store as hundredths;
discounts and tax rates are basis points. Headers and returned lines retain numeric
currency minor units (USD cents) and add `*Minor` strings. Money must fit signed
safe integers; unsupported ranges return 422 before committing mutations.

Replacement PATCH lines preserve the legacy no-discount/no-tax calculation while
retaining `taxRateId`; header-only edits preserve amounts. Number/currency remain
fixed. All writes validate tenant references and strict issue-date locks. Number,
header, lines, links, tallies and audit commit together.

Conversion accepts an empty body for the unbilled remainder, or `{lines:[{
purchaseOrderLineId,quantity}]}` for unique partial physical quantities. Saved
net/tax amounts allocate exactly, preserving discounts and rounding residuals.
Qualified partial orders can subsequently convert their remaining quantities.
Each received slice links once. Reverse-charge VAT is excluded from bill amountDue.
Conversion reserves billed tallies; bill recognition does not reserve again.
Void releases them. Converted bills cannot be edited/deleted through draft CRUD;
void and reconvert. Legacy partially billed orders lacking exact allocation history
return 422 instead of guessing their residuals.

Send requires `approve:bills`; other PO writes require `manage:bills`. Empty send
body marks sent without email. `sendEmail:true` requires recipientEmail, subject and
templateProps. Delivery follows commit; failure returns 502 with sent state retained.
Use document email tools to retry. The legacy attachPdf flag is accepted but no PO
PDF is attached. Invalid JSON/email bodies return 400 before mutation.

Counts add `amountMinor` and `currencyCode` per status. Mixed currency buckets,
unsafe constituents (including offsetting history) and unsafe sums reject 422.
All eight operations have corresponding MCP tools, including draft edit/delete,
detail/counts and send. PDF, full-int64, other procurement contracts and production
currency qualification remain separate.

## Bill bulk exact contracts

POST `/api/v1/bulk/bills/preview` accepts `{source?, rows}`, returning per-line
`{preview, validCount, totalCount}`. POST `/api/v1/bulk/bills/import` also requires
`fileName` and `manage:bills`, returning 201 `{job}`. Inspect processed/error counts
and errorDetails for partial failures. Flat CSV lines group by nonempty
`billNumber`; omission/blank creates separate bills. Grouped supplier, dates and
currency must agree. The group key is never stored as the number or a retry key.

Required fields are `contactName`, `issueDate`, `dueDate` and `lineDescription`.
Supplier names and optional `lineAccountCode` resolve literally within the current
organization; ambiguous/deleted suppliers and missing/inactive accounts fail.
Currency defaults USD. `lineUnitPrice` is numeric/CSV decimal-major price;
`lineUnitPriceExact` is exact decimal-major text; `lineUnitPriceMinor` is integer
currency minor text. Optional extended amount overrides use `lineAmount` (major
units, with grouped CSV money support), `lineAmountExact` or `lineAmountMinor`.
Aliases must agree. Quantity is physical units stored as signed int32 hundredths;
tax remains zero. Prices/products/overrides/group sums must fit safe integers;
unsupported values fail before job creation.

Preview adds stored numeric minor `unitPrice`, `amount`, `taxAmount` and matching
`*Minor` strings. Job totalRows counts input lines; processed/error counts and
error ordinals count documents. Each draft/number/lines/create audit commits
atomically; period/reference/database failures are isolated. Reimport creates new
drafts; inspect before retry. There is no ledger/settlement posting. MCP tools
`preview_bill_import` and `import_bills` share these contracts, and CSV mapping/
template tools expose all aliases. Full-int64/production currency qualification
remains separate.

## Purchase requisition exact contracts

`/api/v1/purchase-requisitions` supports list/create; `/:id` supports GET, draft
PUT and DELETE. Create returns `{requisition}`; detail and edits return a bare
document; list returns `{data,pagination}`. Prices accept decimal-major numeric
`unitPrice` (USD 12.50), exact decimal-major `unitPriceExact` or canonical integer
minor `unitPriceMinor` strings. Aliases must agree. Currency defaults USD; quantities
are physical units stored as signed int32 hundredths. Exact ratios preserve
extended-price rounding; tax is always zero and `taxRateId` is only a reference.
Numeric header and returned line amounts retain currency minor units (USD cents),
with additive `*Minor` strings. Money must fit signed safe integers; unsupported
prices/products/sums/history reject with 422 before mutation.

PUT edits draft supplier, required date, reference or notes. Lines, request date,
currency and number remain fixed. PUT `{status:"submitted"}` submits a draft;
other status changes reject. `/approve` and `/reject` accept only submitted
requisitions; rejection accepts an optional reason. `/convert` accepts only an
approved requisition with a supplier, copying saved money/lines/currency to one
draft PO dated today in UTC and linking it. Repeated conversion rejects.
Approved/converted requests cannot be edited or deleted. DELETE soft-deletes a
draft and retains its historical lines.

Create/edit/delete/submit/convert require `manage:purchases`; approve/reject
require `approve:purchases`. Every write validates tenant references and strict
request-date period/fiscal locks; conversion also checks the new PO date.
Number/header/lines/status/link/audit commit together. No automatic approval
workflow routing or notifications are performed. MCP counterparts include distinct
`update_purchase_requisition`, `delete_purchase_requisition` and
`submit_purchase_requisition` tools, with existing list/get/create/approve/reject/
convert tools. Full-int64 and production currency qualification remain separate.

### Bank statement sessions and undo

| REST operation | MCP equivalent |
|---|---|
| GET / POST `/api/v1/bank-accounts/:id/reconciliations` | `list_bank_reconciliations` / `create_bank_reconciliation` |
| GET `/api/v1/bank-accounts/:id/reconciliation` | `reconciliation_report` |
| POST same path, action `complete` / `adjustment` | `complete_bank_reconciliation` / `post_bank_reconciliation_adjustment` |
| POST `/api/v1/bank-transactions/:id/reconcile` | `reconcile_bank_transaction` |
| POST `/api/v1/bank-transactions/:id/unreconcile` | `unreconcile_bank_transaction` |
| POST `/api/v1/bank-transactions/:id/exclude` | `exclude_bank_transaction` |

Create requires Gregorian startDate/endDate and signed integer **bank currency
minor-unit** startBalance/endBalance or exact startBalanceMinor/endBalanceMinor.
Aliases must agree. USD 1250 is $12.50; JPY/IRR 1250 is 1250, KWD 1250 is 1.250.
Overlapping inclusive windows reject. Session results add exact aliases and
currencyCode. Adjustment numeric amount is signed integer minor units;
amountMinor supplies the agreeing exact string. Safe money/sum/difference range
is +/-9007199254740991; valid larger exact values fail 422 before commit.

Proof names currencyCode for statements and glCurrencyCode for the base ledger.
Monetary totals/scalars/transactions add named Minor strings. Foreign currency
comparison returns difference=null, isBalanced=false and
comparisonUnavailableReason=different_currency_units. Completion and adjustment
currently require base-currency banks. Complete requires reconciliationId and
all accounted nonexcluded window lines, opening-plus-movement closing equality
and a matching GL closing balance. Optional distinct transactionIds cannot omit
unattached window lines or silently include invalid IDs. Mark accepts optional
journalEntryId and reconciliationId, requires an exact matching posted manual
identity-FX base journal, and posts nothing.

Undo preserves pre-existing matched journals and cash payments by detaching them.
Bank-created cash payments restore exact document allocations and soft-delete the
payment; bank-created coding/expense/adjustment/transfer postings get exact saved
FX reversals. Noncash carriers cannot follow the cash path. Transfer undo handles
both reciprocal legs and deletes only proven synthetic movements; imported dates,
amounts and balances stay unchanged. Affected completed sessions reopen. REST
keeps `{transaction}`; MCP undo adds reversalEntryId/deletedTransaction to its
existing diagnostics. Synthetic-row removal is explicit in MCP.

All writes and proof require manage:banking; bank expense undo also requires
manage:expenses. Dates and referenced history must be open and qualified. Writes
and audit commit together. Repeated mark/complete/undo reject; exclude toggles and
adjustment calls create new postings, without replay keys. Inspect records after
an uncertain response before retrying.
