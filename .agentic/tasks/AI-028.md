## Acceptance criteria

- [ ] Execute all six AI_PRODUCT_EXPERIENCE journeys using actual supported domain candidates, scoped ordinary/delegated/site users and deterministic provider fixtures. Record task success, wrong turns, unclear labels, recovery problems, fixes and exact evidence; distinguish agent walkthroughs from any actual human sessions.
- [ ] Verify first-use setup, price/member-budget blockers, connection-test results, capability-based suggestions and no-data/no-access/outage states. A user can find the next action without raw IDs, hidden prerequisites or technical diagnostic knowledge.
- [ ] Exercise keyboard-only and screen-reader milestone behavior, both locales/themes, 360/768/1280 px layouts and 200% zoom, IME, long Persian/Latin/money content, focus return, no clipped controls and project contrast/touch targets. Separate component, actual runtime and native Persian evidence; screenshots/goldens are not required.
- [ ] Verify delayed response after organization switch, expired permissions, double submission, stale/rejected approval, offline reconnect, stop during action, uncertain writes and long/paginated histories. UI summaries agree with persisted service results and real permitted record links; no fabricated success or retries.
- [ ] Verify usage/filter/export consistency, unknown/reserved costs and UTC resets in local presentation, transcript privacy and setup/operations distinctions. Refresh user-facing supported capability labels after AI-014..021 and verify at least one concrete scenario per domain task, including AI-016's actual approval-gated expense posting with exact ledger assertions in the disposable test environment.
- [ ] Fix blocking usability/accessibility defects before acceptance; link any remaining bounded work with severity, owner task and explicit scope. Do not waive existing native-language/security/production gates or substitute fixture success for live-provider qualification.

No live calls or deployment inferred. Run controller validation and diff checks.
