# AI-025 - Make AI policies and sensitive settings understandable

## Objective and implementation scope

Improve existing organization/agent policy and sensitive-settings interactions. Keep ordinary chat separate from management, preserve canonical tool names and use the live reviewed registry as the capability source.

## Inputs

- [Owner requirements](../sources/SOURCE.md#ai-agent-and-administration-owner-extension).
- [Product experience contract](../docs/AI_PRODUCT_EXPERIENCE.md) and [delivery plan](../docs/AI_AGENT_PLAN.md).
- Actual source, current shared REST/MCP services and dependency evidence. Verify interfaces before implementation.

## Acceptance criteria

- [ ] Present tool policy choices grouped by business domain and effect with search, localized labels/help and effective user/org/agent intersection. Distinguish not implemented, not permitted and disabled by policy without exposing inaccessible record data.
- [ ] Support explicit selection and a before/after impact review of changes. No broad select-all default or policy preset silently grants sensitive/new operations; unsupported and privileged administration tools remain excluded from ordinary chat.
- [ ] Show scope and affected default agent/organization clearly. Credential revocation and provider/policy disablement have concrete confirmations with affected configuration and run consequences; existing operational stop remains readily available and does not imply undo.
- [ ] Track dirty state per form; saving one card cannot silently discard another card's edits. Handle conflict/reload/reapply, cancellation, duplicate clicks, permission revocation and organization switching with accessible focus and localized inline feedback; clear secrets rather than preserving them.
- [ ] Expose any new policy/readiness metadata through shared scoped REST/MCP operations and update catalogs when AI-014..021 add reviewed capabilities. Exercise role-specific component interactions, delayed-response org switches, keyboard confirmations and both locales/themes; do not claim browser or native review from source assertions.

## Verification

Record exercised viewports/locales/themes and observable outcomes. Use existing authorized runtime or a component harness; no full builds or unrequested dev server. No live calls or deployment inferred. Run controller validation and diff checks. Split through the controller before implementation if the scope exceeds a coherent change; the parent retains independent acceptance.
