# AI-004 - Manage AI provider credentials models and configuration

## Objective and implementation scope

Implement shared provider configuration services with REST/MCP parity and a provider adapter boundary.

This task implements the owner-requested AI feature; it does not authorize deployment or relax existing financial/release gates.

## Inputs

- [Owner requirements](../sources/SOURCE.md#ai-agent-and-administration-owner-extension).
- [Architecture and delivery plan](../docs/AI_AGENT_PLAN.md).
- Actual source and dependency evidence; verify current contracts before editing.

## Acceptance criteria

- [ ] Site administrators configure enabled providers, approved endpoints, models, defaults, timeouts and model capabilities; organization administrators may only use delegated configuration scope.
- [ ] API credentials are encrypted server-side with external key management, masked on reads, rotatable and revocable; never return credentials in logs, prompts, browser state or tool output.
- [ ] Connection tests and provider requests enforce endpoint allowlists, redirect and private-network restrictions, timeouts and sanitized errors; provider switching and disabled configurations are tested.
- [ ] Provide operation-specific MCP tools and REST endpoints for authorized management, using shared services and described strict input schemas; provider administration is excluded from ordinary chat tool discovery.

## Verification

Run meaningful focused checks for the changed contracts, including real REST/MCP authorization and disposable-database integration where relevant. Use typecheck and lint for application changes, catalog validation for localized UI, controller validation and diff checks. No full build or unrequested dev server. Record executed checks and limitations in unique evidence; do not substitute mocked-provider success for live-provider qualification.
