Source inventory and unsupported scope: [capability matrix](../registries/AI_CAPABILITY_MATRIX.md). Requirements: [owner extension](../sources/SOURCE.md#ai-agent-and-administration-owner-extension). Actual task status remains in task metadata.

## Runtime and state ownership

Choose a PostgreSQL-backed durable queue with a separately invoked Node worker for agent execution. Next request handlers authenticate, validate, persist and enqueue; streamed HTTP/SSE connections only observe persisted events. Existing Trigger.dev jobs may wake the queue through a thin adapter after configuration/host availability is qualified, but Trigger credentials or a browser connection are not required for the core state machine. Existing `trigger.config.ts` has a placeholder project fallback and 1800-second maximum; this is not evidence of a deployed worker. AI-007 must supply an explicit worker entrypoint, polling/lease recovery and graceful shutdown; AI-013 must qualify its actual process hosting. Do not run the worker or deploy infrastructure during this planning task.

AI-003 persists conversations, messages, runs, steps, approvals and outbox events with opaque IDs, organization/owner scope, UTC timestamps and version numbers. Queue claims use bounded leases, heartbeat and compare-and-swap versions; one active executor owns a run. Stable run/client request keys prevent duplicate submissions. Monotonic event sequence numbers permit reconnect without replaying effects. Enqueue and run creation commit atomically. Durable state, never model narration or a transcript summary, determines success.

| Run state | Allowed next states / conditions |
|---|---|
| `queued` | `running` after atomic lease claim; `cancelled`/`expired` before work starts |
| `running` | `awaiting_approval`, `awaiting_input`, `queued` for a bounded safe retry, `succeeded`, `failed`, `cancelled`, `expired`, `reconciliation_required` |
| `awaiting_approval` | `queued` only after authorized unexpired matching approval; `cancelled`, `expired`, `failed`; no held worker lease |
| `awaiting_input` | `queued` after owner answer validated against current scope; `cancelled`, `expired` |
| `reconciliation_required` | `queued` after verified outcome reconciliation and new authorization/approval where needed, or `failed`/`cancelled`; never automatic write replay |
| `succeeded`, `failed`, `cancelled`, `expired` | Terminal; a follow-up creates a new run referencing the original. Completed effects remain visible. |

Step states: `prepared -> executing -> succeeded/failed/uncertain`; `prepared -> skipped` on cancellation or policy refusal. A timed-out write/worker crash after dispatch becomes `uncertain` and places the run in `reconciliation_required` unless a durable operation key/record can prove its outcome. Never mark success because the provider says so. Results record actual record IDs and operation status; partial success survives later failure. An approval request does not represent execution. Cancellation/kill switch is rechecked before provider requests and each tool dispatch; it prevents further work and records already committed effects without claiming rollback. In-flight writes complete or reconcile at safe transactional boundaries.

Initial configurable hard ceilings: 20 tool dispatches/run, 8 provider requests/run, 120-second provider timeout, 10-minute run execution deadline excluding user wait, 24-hour input wait, 15-minute approval expiry, one active run/user and two active runs/organization. Use provider-specific context/token limits; start with a maximum 4,096 output tokens/request and enforce lower configured/provider limits. Context budgeting includes schemas, inputs, tool results and reserved output. AI-005 atomically reserves concurrent token/cost budgets before requests; missing usage becomes unknown/reserved pending reconciliation, never zero. AI-007/012 must test ceilings/retries and fairness. These defaults can be lowered by policy and are not performance claims.

## Identity and permissions

Trusted server state chooses actor, credential and organization; reject model-supplied identity/organization fields. Resolve live actor/membership/advisor grants, credential expiry/revocation and custom role in the correct organization before tool discovery, every dispatch, retry, resume and approval execution. Store original credential identity/reference (never secret) to revalidate it. An API/MCP credential cannot gain global/site-admin powers. Discovery filters improve usability; authorization is enforced again inside shared services. Cross-organization references, removed members, missing/mismatched custom roles and stale grants fail closed. Advisor restrictions are enforced from current advisor grants, not the ordinary member role alone. AI-002 supplies the reusable resolver and negative REST/MCP tests; known current fallback gaps are not accepted behavior for the agent.

Proposed permission names follow existing `verb:resource` syntax in `lib/plans.ts`; AI-002/006 and the owning UI tasks must register them explicitly before use. Unknown names currently deny non-owner legacy roles; owner wildcard behavior must still obey enabled flags and site-admin boundaries. A custom role is explicit permission enumeration; no implicit grants from legacy role fallback.

| Permission | Scope and intended legacy default when implemented |
|---|---|
| `use:ai` | Start/reply to own organization runs; member+ plus allowed policy and domain rights |
| `view:ai-history` | Own conversations/results and own usage only; member+ |
| `cancel:ai-runs` | Cancel own runs; member+; broader org cancellation requires `manage:ai-policy` |
| `view:ai-usage` | Organization aggregate usage/errors/latency; admin+; excludes transcript and tool payloads |
| `audit:ai-transcripts` | Explicit organization transcript audit; owner-only default; access itself audited |
| `manage:ai-policy` | Organization enablement, budgets, retention and user access; owner-only default; no provider secrets or site administration |
| `manage:ai-providers` | Organization-scoped configured provider/model connection; owner-only default, masked secret write/rotation, never read plaintext |

Global provider administration additionally requires a current site-admin session through the platform boundary; organization ownership or this permission is insufficient. Ordinary chat cannot discover provider/policy/role/security tools, approve itself or change its budget. New administration REST features need corresponding restricted MCP operations under existing conventions; platform-global operations cannot be invoked through organization-scoped credentials.

## Approval and tool policy

AI-006 entries must contain exact MCP name/schema, shared service, domain permissions, resource-version checks, money contract, output limits, side effects, idempotency strategy and approval class. Unlisted entries deny. The service receives fresh `AuthContext`, uses direct Drizzle/shared domain behavior and returns actual structured results wrapped by existing MCP error/wire conventions; no HTTP self-calls. A result error is not a successful write. Provider/tool-result text is untrusted data, never policy. Reject unknown tools, malformed arguments, forged scope and model-created approvals. All required Zod fields have descriptions and each operation has one purpose.

Automatic class: scoped reads and validated draft preparation only after domain review, with bounded result disclosure. Approval class: posting, voiding, paying, stock/valuation changes, conversion with ledger effects, destructive deletion/merge/purge, outbound sending/sharing/export, schedules, approvals and access/configuration changes. Existing business approval workflows remain additional gates. A draft that reserves stock, sends notifications or causes accounting effects is sensitive regardless of name. Policy may require approval for any further class but cannot relax mandatory domain controls.

Prepare the concrete action first: display operation, affected record IDs/versions, destination/recipients, dates, exact amounts/currencies, consequences and finite batch items. Persist approval hash over canonical validated arguments plus tool/schema version, actor, organization, resources/version, policy/config version and expiry; bind approver identity and scope. Approval requires the actual authorized user interaction, not a model message. Any changed input/resource/policy/permission invalidates the preview and requires another approval. Consume approval once with compare-and-swap tied to the operation key. Batch authorization covers only the displayed finite set, with item-level outcomes. AI-008 implements replay/expiry/race/permission-change tests. Never automatically retry uncertain non-idempotent writes such as `record_bank_transfer`.

## Provider adapter and data boundary

Provider-neutral interface: `capabilities(configVersion)` returns supported text/streaming/function-call/strict-schema/usage/cancellation features and explicit limits; `generate(request, signal)` emits ordered text deltas, tool-call deltas/completed calls, usage and a final reason (`completed`, `tool_calls`, `length`, `cancelled`, `error`). Request has server-controlled model/config snapshot, bounded public messages/tool results, allowlisted schemas and token limit; credentials remain inside the adapter. Completed call IDs must be unique and arguments fully buffered/validated before dispatch. No action executes from partial JSON. Unknown finish reasons/missing usage/malformed events fail safely. Provider errors normalize auth, rate-limit/retry-after, timeout, network, context-limit, unavailable-model and invalid-schema outcomes without leaking secrets. Retry only safe model requests within budgets, recording each attempt; never silently switch provider or model.

Versioned configurations hold adapter kind, approved endpoint/model ID, capability evidence date, credential reference/key version, pricing version and allowed data categories. Fixed approved HTTPS endpoints first; custom endpoints require DNS/IP validation on connection, blocked private/link-local/metadata ranges, no redirects/credential forwarding and an explicit administration policy. Transport credentials are not model/tool arguments. No automatic fallback endpoint, remote MCP delegation, arbitrary URL-fetch or provider-managed tools. First adapter supports local application function dispatch with sequential calls (`parallel_tool_calls: false` where supported). Unsupported structured schemas/models are rejected before a run starts. Missing deployment/provider qualification disables live calls while deterministic adapter fixtures support engineering tests.

## Visibility, retention and safe presentation

Conversation content and full results are private to creator plus separately authorized transcript auditors in that organization. Aggregate usage permission exposes counts/cost/status/latency only, never prompts, tool arguments, customer/payroll records or output snippets. Audit access logs include actor/org/reason/time. Members who lose organization access cannot retrieve old histories. Existing domain permission changes also restrict any historic result disclosure: redact inaccessible record payloads instead of preserving a backdoor snapshot. User-visible output contains progress, tool names/status, concrete approvals, actual record links and partial/final outcomes; no private model reasoning, provider credentials or system secrets. English/Persian catalogs, safe text/Markdown rendering, no executable HTML, URL allowlisting, RTL and keyboard accessibility belong to AI-009/010.

Initial local retention defaults: 30 days for message content and bounded redacted tool payloads; 90 days for content-free usage/run/audit metadata. Cap each persisted prompt/tool result at 64 KiB UTF-8 and aggregate run payload at 1 MiB; truncation is marked with digest, byte count and record IDs and cannot become execution authority. Minimize data before provider transmission; no full backups, credential/token values, binary uploads or unbounded customer/payroll dumps. Apply structured field-based secret redaction before persistence, transport logging and exports, plus defensive scrubbing for unstructured content. Raw reasoning traces are never collected. Encrypt provider keys server-side with a separately configured encryption key and versioned rotation; missing key fails closed. No plaintext secret retrieval endpoint, credential in config snapshot or encryption key stored alongside its ciphertext.

Deletion requests stop new runs, cancel/wait/reconcile active effects, tombstone the conversation and enqueue idempotent payload erasure; no deletion of underlying financial/business records. Expiry/purge workers clear content and approval payloads after the applicable deadline while retaining only necessary content-free outcome references within metadata retention. Expired/consumed approvals cannot be revived by a summary. Usage aggregates retain no content and remain within organization scope. Backup copies obey the deployment's documented expiry/restore-erasure process, with no promise of immediate removal from immutable backups; AI-013 must verify that process and configured retention. These are engineering defaults, not a statutory retention determination, and no existing audit/financial retention policy is shortened.

## Rollout and acceptance boundaries

`AI_ENABLED` is proposed false by default; missing flag/config, missing encryption key, unavailable worker, unqualified provider/model or global kill switch prevents new runs. Organization opt-in is a second false-by-default restriction. Configuration/policy snapshots remain immutable per run; a stricter current policy/kill switch wins. AI-013 controls rollout after AI-012 security, accounting/reliability qualification and actual configured-provider smoke test, plus all applicable owner/production-release approvals. AI technical completion changes no IRR/financial readiness flags or Stripe scope. Mocked provider success never means live-provider acceptance.
