# AI-002 - Enforce live identity and permissions for agent tool calls

## Objective and implementation scope

Harden and qualify identity resolution across session, API-key and MCP access, including custom roles and advisors.

This task implements the owner-requested AI feature; it does not authorize deployment or relax existing financial/release gates.

## Inputs

- [Owner requirements](../sources/SOURCE.md#ai-agent-and-administration-owner-extension).
- [Architecture and delivery plan](../docs/AI_AGENT_PLAN.md).
- Actual source and dependency evidence; verify current contracts before editing.

## Acceptance criteria

- [x] Removed members and revoked or expired credentials fail closed; MCP custom-role permissions are resolved from current scoped membership without stale-role fallback.
- [x] Every execution and resumed approval revalidates identity, organization, effective permissions and resource scope; tool filtering cannot replace server authorization.
- [x] Negative REST/MCP tests cover custom roles, advisor limitations, cross-organization IDs, revocation during a run, forged organization arguments and site-admin versus organization-admin separation.

Record executed checks and limitations in unique evidence; do not substitute mocked-provider success for live-provider qualification.

## Handoff

Implemented current scoped membership/custom-role resolution for REST and MCP, credential-reference revalidation, dispatch/retry/resume authorization helper, session revocation/expiry and bounded external-advisor grants. `wrapTool` revalidates authenticated credential-bound contexts before invoking existing handlers. API-key UI organization headers remain ignored in favor of the immutable credential scope; explicit server-required organization mismatches reject. Existing MCP custom roles now follow current membership rather than token snapshots.

`lib/api/execution-identity.ts` exports `executionIdentity`, `resolveExecutionIdentity` and `authorizeExecution`. AI-003 must persist server-created references only; AI-006/007 must call `authorizeExecution` with the server-owned organization and registered operation permission before every dispatch/retry/resumed approval, then retain domain resource checks. A reference is not user/model input and does not itself approve execution. Internal trusted contexts without transport bindings are retained for existing services/tests; new agent execution must use the credential-reference boundary. Existing run/approval runtime is not present yet, so its actual wiring and race/recovery qualification remain with those dependent tasks.

No provider, rollout, schema, financial or Stripe changes. See unique attempt/review evidence for executed checks and limitations.
